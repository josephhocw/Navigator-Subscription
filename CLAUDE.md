# RHO Navigator — Website & Stripe Webhook

## Identity

This repo (`josephhocw/Navigator-Subscription`, branch `main`, deployed on Vercel) is the RHO Navigator subscription website **and** the Stripe webhook that runs the whole subscription back office. The webhook replaced a set of Zapier automations in June 2026 — it is now the sole automation. On every Stripe event it: updates a Google Sheets subscriber database, sends a customer email via Resend, and pings Joseph on Telegram.

The marketing site is an Astro app under `web/` (rebuilt June 2026; the old root-level HTML site is retired). The back office is TypeScript Vercel serverless under `api/` + `lib/`.

> This repo is nested inside a larger workspace (`Navigator Business/`) that gitignores it, so the broader business context — pricing strategy, the Telegram bots, secrets map — lives one level up and is **not** in this repo. If you have it locally, see `../CLAUDE.md`, `../Navigator Business Resources/business-workflow.md`, and `../Navigator Business Resources/secrets-map.md`.

## Webhook architecture

Four layers; everything past the translator speaks the subscriber domain, not Stripe shapes. Keep this separation — it's what makes the lifecycle unit-testable without Stripe payloads.

| Module | File | Job |
|---|---|---|
| Edge | `api/stripe-webhook.ts` | Receive request, verify the `stripe-signature`, call the translator, dispatch the resulting actions to the lifecycle. Owns nothing else. Satisfies the `Mailer` / `AdminNotifier` interfaces with plain object literals. |
| `EventLog` | `lib/event-log.ts` | The lifecycle's fourth collaborator: append-only history, one row per lifecycle event, written to the **Status Log** tab (`SheetsEventLog`). This is the churn/renewal/cohort record — the Subscribers tab updates in place and forgets history. Log writes run inside `runSideEffects`, so a failed append alerts Joseph but never fails the webhook. Never edit or delete Status Log rows. |
| `StripeEventTranslator` | `lib/stripe-translator.ts` | Pure transform: `Stripe.Event` → a list of `SubscriberAction` values. May call back into Stripe (e.g. retrieve a subscription/schedule) but never touches the store, mailer, or notifier. No business rules. |
| `SubscriptionLifecycle` | `lib/subscription-lifecycle.ts` | Every per-action business rule: which fields to write, which email to send, which admin ping to fire. Driven by `apply(action)`. Knows nothing about Stripe. Collaborators (`store`, `mailer`, `notifier`) are injected. |
| `SubscriberStore` | `lib/subscriber-store.ts` | Storage seam. `SheetsSubscriberStore` is the Google Sheets implementation; patches accept real `Date` objects and the store formats them on write. Wraps `lib/sheets.ts`. |

Supporting modules: `lib/plans.ts` (price-ID → plan mapping, prices, display names, plan-change classification, invite links), `lib/format-date.ts` (the single place dates become display strings — `"16 April 2026 18:00"` Singapore time).

**TradingView access automation** (`lib/tradingview-access.ts` + `lib/tradingview-reconcile.ts`): grants/removes invite-only script access by driving TradingView's private "Manage Access" endpoints with a logged-in session cookie (`TRADINGVIEW_SESSIONID` / `_SIGN`) — there is no official API. One script per plan (8 total; `PLAN_TO_PINE_ID`). The lifecycle grants on STARTED, swaps scripts on PLAN_CHANGED, and removes on ENDED, injected via the `TradingViewGranter` seam (`NoopTradingViewGranter` when cookies are absent → manual fallback + warning). Each grant/remove fires a per-action admin ping (✅/🗑️/❌). Grants are **permanent** (no expiry); only a full cancellation loses access, mirroring the Telegram bot. A daily Vercel cron (`api/tradingview-reconcile.ts`, `0 3 * * *` in `vercel.json`) diffs the sheet against the live grantees on all 8 scripts and fixes drift. **Reconcile only ever acts on usernames present in the sheet** — comps to non-sheet users are safe, but a subscriber granted a script beyond their sheet plan is removed from it.

**Telegram group removal** (`lib/telegram-groups.ts`): removes a cancelled subscriber from the Telegram groups they've lost, at the moment their subscription ends, instead of waiting for the bot repo's `scheduler.py` sweep at 12:00 PM SGT — previously a cancelled subscriber kept group access for up to 24 hours. It's a TypeScript port of the bot's `access.py` decision logic: any row not in the barred set (`CANCELLED` / `TRIAL_CANCELLED`, per `access.py`'s `BARRED_STATUSES`) for the same Telegram username keeps the markets it covers plus the `MAIN` pseudo-market (the open "RHO Navigator Subscribers" group), so a second live subscription can't be removed by a cancelled one; plan→market resolution reuses `parsePlanType()`, so there's no new plan duplication. Injected as a **sixth** lifecycle collaborator via the `TelegramGroupRemover` seam (`NoopTelegramGroupRemover` when `TELEGRAM_BOT_TOKEN` is unset or no `TELEGRAM_CHAT_*` parses — `buildTelegramGroupRemover()` in `api/stripe-webhook.ts`), and reuses `TELEGRAM_BOT_TOKEN` — the same bot the Python access bot runs on, already an admin in all five groups, so no new credential. **It only ever acts on the one subscriber it's handed and never enumerates group membership**, so someone with no sheet row (a friend given free group access by hand) is unreachable by it. Four fail-safe short-circuits fire in this order — whitelisted (`TELEGRAM_KICK_WHITELIST`) → blank Telegram User ID (col P) → blank Telegram username (col D) → unrecognised plan string on a live row — each removing nothing and pinging instead; the unrecognised-plan guard exists because a typo like `"HK "` parses to the unknown category, matches no group, and would otherwise target every group and strip a paying subscriber — deliberately safer than the Python bot, whose `plan_markets()` returns `[]` for an unknown plan and over-removes in exactly that case. The ending row is excluded from its own entitlement calculation deterministically (by `rowIndex`, else a non-blank `stripeSubscriptionId`), so a stale sheet read can't leave the removal a silent no-op. A kick is ban + unban (`only_if_banned: true`); if the unban fails twice the group lands in `outstandingBans` and is pinged "🚨 STILL BANNED — unban by hand", because a banned user cannot rejoin and nothing else in the system heals that. A `getChatMember` error from Telegram itself (`TelegramApiError`) means "never seen this user in this chat" and is skipped quietly; a transport or parse failure is rethrown and recorded as a real failure, because `scheduler.py` sweeps rows whose statuses are all barred (`CANCELLED` / `TRIAL_CANCELLED`) only and does not back-stop a partial cancellation (one of several subscriptions ending while the person stays ACTIVE). A fifth check runs per group, after the entitlement maths: entitlement is computed from col D (the username) but the kick executes against col P (the User ID), so `getChatMember`'s reported `user.username` is compared against col D — a mismatch means col P points at a **different person** (col P is hand-filled on comp rows), and that group is skipped and reported in `identityMismatches` rather than banned. A user Telegram reports with *no* username is not a mismatch (they may never have set one), so that proceeds. Fires on `ENDED` **and on plan changes** (see the migration paragraph below — `PLAN_CHANGED` upgrade/switch, the downgrade-executed path, and the RENEWED period-boundary confirm), never `CANCELLATION_SCHEDULED` or `DOWNGRADE_SCHEDULED` — a scheduled change keeps access until the paid period ends — and `lib/comp-expiry.ts` writes `CANCELLED` directly without emitting `ENDED`, so an expiring comp is still swept on the daily cadence (`scheduler.py` today; the noon sweep below after cutover), not instantly. Behind `TELEGRAM_KICK_DRY_RUN`, which **fails safe: only the literal `false` (trimmed, case-insensitive) goes live — unset, blank, a typo, or a var scoped to Preview only all stay in dry-run.** Going live is a deliberate act. Dry-run results also carry a `configSummary` (counts only: groups loaded, usernames whitelisted) appended as a quiet trailing ping line, and `buildTelegramGroupRemover()` `console.warn`s if the whitelist is empty — legal, but it means nobody is protected. **The ping is never the only record:** every removal that returns a result — short-circuits included, skipped only when the remover isn't configured or `removeFromGroups` itself threw (nothing was removed in that case, and the catch pings) — writes a `TELEGRAM_REMOVED` console line *and* a `TELEGRAM_REMOVED` Status Log row (Detail prefixed `dry run — ` in dry-run) before any ping fires, so a Telegram outage, a wrong `ADMIN_CHAT_ID` or an HTML parse error can't make a removal invisible. Free text interpolated into these pings (both handles, the email, the col-P User ID, error and mismatch strings) is HTML-escaped by `escapeHtml` in `subscription-lifecycle.ts` — `lib/telegram.ts` sends `parse_mode: "HTML"`, a stray `<` in a hand-typed cell makes Telegram reject the whole message, and `pingTv` swallows that to `console.error`, silently losing the alert.

**Telegram bots → Vercel migration (in flight — runbook: `docs/runbooks/telegram-migration-cutover.md`):** three pieces built 2026-08-05 replace the VPS Python bots and close the plan-change gap; until cutover the `bot.py`/`scheduler.py` references elsewhere in this file describe the still-running pre-migration world and are removed at retirement. **(1) Join guard** (`api/telegram-webhook.ts` + `lib/telegram-join.ts` + `lib/telegram-access.ts`), replacing `bot.py`: Telegram webhook mode — `setWebhook` registers the endpoint with a `secret_token` (`TELEGRAM_WEBHOOK_SECRET`; requests whose `X-Telegram-Bot-Api-Secret-Token` header doesn't match are 403'd, and the endpoint otherwise always answers 200 so Telegram never replays an update) and `allowed_updates: ["chat_member"]`, so Telegram pushes every membership change in the five groups within seconds. `telegram-access.ts` is the pure port of `access.py`'s join-evaluation half (market groups strict: no-username/not-found/all-cancelled/wrong-plan kick; main group lenient: guests welcome, only fully-CANCELLED subscribers barred; unrecognised live plan fails safe = allow + ping, same divergence as the remover) and `telegram-join.ts` orchestrates the verdict: kick via the shared `kickFromChat` ban+unban path, or allow + write the joiner's User ID to col P of every live row. **Fails open on a sheet outage** — the joiner is allowed and Joseph pinged; never kick because Google hiccuped (the sweep corrects within a day). Behind `TELEGRAM_JOIN_DRY_RUN` (same only-the-literal-`false` semantics; dry-run also suppresses col-P writes, since `bot.py` owns col P until cutover). **(2) Daily sweep** (`api/telegram-sweep.ts` + `lib/telegram-sweep.ts`, cron `0 4 * * *` UTC = noon SGT, existing `CRON_SECRET` auth), replacing `scheduler.py` and deliberately EXTENDED: where `scheduler.py` only kicked fully-barred rows, the sweep reconciles EVERY distinct username with a col-P User ID against the union of their live rows' entitlements — so plan-change drift, missed webhook events and hand-edits self-heal daily, mirroring the 3am TradingView reconcile (guests with no sheet row remain untouchable; all whitelist/mismatch/ban-unban safety lives in the shared remover). A time-budget-tripped partial run rotates its start point by calendar day so the tail of the list is never starved, and a col-P User ID claimed by two different usernames is skipped for both and pinged (data-entry error — don't guess the owner). Behind `TELEGRAM_SWEEP_DRY_RUN` (same fail-safe semantics). **(3) Instant plan-change kicks:** the lifecycle now calls the remover on `PLAN_CHANGED` (upgrade/switch and downgrade-executed paths) and on the RENEWED period-boundary plan-change confirm (guarded so the marker-confirm delivery order can't double-kick), with the subject row's plan OVERRIDDEN in memory to the NEW value — a stale sheet read showing the old plan would re-grant exactly the markets being removed. An upgrade that loses no markets skips the remover entirely (old markets ⊆ new = nothing to kick). Rides the existing `TELEGRAM_KICK_DRY_RUN` flag and produces the same `TELEGRAM_REMOVED` log/ping trail.

**Config duplicated from the bot repo (keep in sync, like `plans.ts`):** the five group chat IDs (`TELEGRAM_CHAT_*`) and the kick whitelist (`TELEGRAM_KICK_WHITELIST`) mirror `GROUPS` and `WHITELIST` in the bot's `config.py`. Change both. This duplication disappears if the bots are migrated onto Vercel. That migration is now in flight (join guard, sweep and plan-change kicks above) — this section dies when the VPS bots are retired at the end of it; see `docs/runbooks/telegram-migration-cutover.md`.

**Comps / fixed-expiry access** (`lib/comp-expiry.ts`): complimentary access (e.g. the TCM course's 2-month ALL_MARKETS grant) is modelled as an ordinary subscriber row for the same person with a **blank Stripe Subscription ID** (col O) — the blank ID is what marks it a comp vs. a paid sub — and a fixed expiry in col L. Reconcile unions plans across a username's rows, so the comp row keeps the extra script alive. The reconcile cron runs `expireDueComps` **first** each day: any comp whose col-L expiry (parsed as SGT) has passed is flipped to `CANCELLED` (Latest Action `COMP_EXPIRED`, logged to Status Log), so the same run's reconcile removes the script and the Telegram bot's noon kicker drops the person from groups they're no longer entitled to (a still-active paid row keeps whatever it covers). The reconcile ping gains an "⏰ Comps expired" section. For the Telegram kick to fire, the comp row needs the person's User ID in col P — the join guard writes it when they (re)join; pre-fill it for someone already in the groups.

### `SubscriberAction` (the union the translator emits, the lifecycle consumes)

One Stripe event may produce 0, 1, or several actions.

| Kind | Triggered by | Lifecycle behaviour |
|---|---|---|
| `STARTED` | `checkout.session.completed` (subscription mode) | Append a row, or update in place + tag `REACTIVATED` if the email exists. A trial sign-up (`isTrial`) writes Status `TRIAL_ACTIVE` and Latest Action `START_TRIAL`; a paid sign-up keeps Status `ACTIVE` and Latest Action `NEW_SUBSCRIPTION`. Onboarding email + admin ping. Carries `referralSource` (the session's `client_reference_id`) → col T + subscription `metadata.ref`; the ping gets a "Referred by" line. **Username validation (2026-07-27):** the TradingView username is checked via the granter's optional `validateUsername` (public `username_hint` — independent of the session cookie, so a null means the username is wrong, never that our auth is) BEFORE the onboarding email. Wrong or missing → `tvUsernameInvalid` flags the email's attach step ("WhatsApp 8200 7039 / Telegram @Joseph_Ho with your correct username"), the grant is skipped, and a ⚠️ invalid-username ping fires. Lookup error or Noop granter → fail open (normal email, grant attempted as before). |
| `RENEWED` | `invoice.payment_succeeded`, `billing_reason=subscription_cycle` | Refresh dates, bump `subscriptionCount`, reset `failedPaymentCount`. Admin ping (silent otherwise). Carries the plan the invoice charged for: if it differs from the sheet, a period-boundary plan change hasn't been processed yet (event order isn't guaranteed) and this handler applies it — plan, price, coupon, plan-change email + ping. Skips duplicate deliveries (sheet expiry already matches). Note: a trial's first charge is also `subscription_cycle`, so RENEWED does the date/count bookkeeping at conversion too — the welcome email is owned by `TRIAL_CONVERTED` (below), not here. |
| `TRIAL_CONVERTED` | `customer.subscription.updated`, status `trialing → active` **AND `latest_invoice` is `paid`** | A free trial's first successful charge. Sends the "you're now a full subscriber" welcome that reveals the announcement channel + signal groups (both withheld during the trial) + admin ping + Status Log entry. Does NOT touch dates/count (RENEWED owns that on the same charge), so the two are order-independent. Plan/next-billing come from the action (the live subscription), so a trialist who downgraded mid-trial gets the right groups. |
| `PLAN_CHANGED` | `customer.subscription.updated` with `items` in `previous_attributes` | Resolve old plan from the store, classify UPGRADED / DOWNGRADED / PLAN_SWITCH by price. Sheet update + email + admin ping. Downgrades write the transient `DOWNGRADE_EXECUTED` marker instead and defer email + ping to the confirming `RENEWED`, which flips it to `DOWNGRADED`. Same-plan events (price-ID migration, or the late half of the order race) sync price/coupon + ping only — no customer email. |
| `DOWNGRADE_SCHEDULED` | `customer.subscription.updated` with a `schedule` newly attached | Tag the pending downgrade; Current Plan stays until the scheduled date. Email + admin ping. |
| `CANCELLATION_SCHEDULED` | `customer.subscription.updated`, `cancel_at_period_end` false → true | Set expiry to access-end date. Cancellation email (Undo button → billing portal) + admin ping. |
| `CANCELLATION_UNDONE` | `cancel_at_period_end` true → false | Status → ACTIVE, `UNDO_CANCELLATION`. Admin ping only. |
| `ENDED` | `customer.subscription.deleted` | Status → `TRIAL_CANCELLED` when EITHER `wasUnconvertedTrial` is set OR the row itself still reads `TRIAL_ACTIVE` / `TRIAL_CANCELLATION_SCHEDULED`; otherwise `CANCELLED`. The win-back email choice stays keyed on `wasUnconvertedTrial` alone (see below) — it can diverge from the status write. **Duplicate-delivery guard (2026-08-03):** if the row already reads `CANCELLED` **or** `TRIAL_CANCELLED`, log one console line and return — no sheet write, email, log row, ping or access removal. Stripe only redelivers after a non-2xx, and the only steps that can throw (`requireSubscriber`, `store.applyUpdate`) both run *before* the status becomes `CANCELLED`/`TRIAL_CANCELLED`, so either value reliably means the first delivery completed. Without it a redelivery re-sent the "your subscription has ended" email that `wasScheduled` had deliberately suppressed — on the second pass the status is `CANCELLED`, not `CANCELLATION_SCHEDULED`, so the suppression silently stopped applying. Remove TradingView access (grants are permanent, so this is the point they lose it) and remove Telegram group access for whatever markets the subscriber is no longer entitled to (`lib/telegram-groups.ts`, see above). Admin ping. **Win-back branch:** the translator sets `wasUnconvertedTrial` when the sub had a trial and **never charged** (a paid sub always charges at checkout, so "never charged" = unconverted trial); that sends the win-back email instead of the normal "subscription ended" email. |
| `PAYMENT_FAILED` | `invoice.payment_failed` | Increment `failedPaymentCount`. Payment-failed email + admin ping. |
| `DOWNGRADE_UNDONE` | `customer.subscription.updated`, schedule released with items unchanged (see gotcha below) | `UNDO_DOWNGRADE`. Downgrade-undone email + admin ping. |
| `CANCELLATION_REASON_RECEIVED` | `customer.subscription.updated` with only `cancellation_details` changed | Admin ping with the reason; no sheet write. |
| `COUPON_CHANGED` | `customer.subscription.updated` with `discounts` changed, items unchanged | Update price + coupon code (col J). Admin ping only. |

**Downgrade-executed gotcha (already handled — don't re-open):** when a scheduled downgrade fires at period end, Stripe sends two `customer.subscription.updated` events — the items change (correct) and the schedule release. With `end_behavior: "release"` the schedule status is `"released"` in *both* the natural-completion and manual-undo cases, so status can't disambiguate. The translator compares the subscription's current price ID against the schedule's phase-1 target price: match → already executed, skip; mismatch → subscriber cancelled the pending downgrade, emit the undo.

### Other event-handling notes

- **Payment-link sessions:** checkouts come from Stripe Payment Links (one per plan), not API-created sessions. `customer_email` can be **null** on those, so the translator uses `customer_details.email` as the dedup key. The TradingView/Telegram custom fields must be configured per payment link in the dashboard to appear in `custom_fields`.
- **Downgrade *scheduled* detection:** the customer portal queues a downgrade as a subscription schedule, so `previous_attributes.schedule` goes `null` → schedule ID while `items` is absent (items haven't changed yet). That's the signal for `DOWNGRADE_SCHEDULED`; resolve the effective date from `phases[0].end_date` (fallback `current_period_end`).
- **Events deliberately ignored:** `customer.subscription.created` (redundant — checkout covers new subs), `customer.created`, `invoice.created`, `payment_intent.*`, and `charge.refunded` (refunds are handled manually in Stripe — no sheet/notification automation). They're logged and dropped.

### Free trials (general — any trial, not just the 25 July cohort)

The trial flow keys off Stripe's trial *mechanics*, so any trial the business runs gets it automatically. The only cohort-specific content left in the trial *welcome-at-signup* variant is the trial-end date (9 Aug for the 25 July cohort, 16 Aug for DrWealth — both self-expiring hardcodes in `lib/email.ts`); the conversion and win-back emails are cohort-agnostic. Three moments:

1. **Sign up with a trial** → `STARTED` with `isTrial` (subscription arrived `trialing`); writes Status `TRIAL_ACTIVE` and Latest Action `START_TRIAL` (a paid sign-up writes `ACTIVE` / `NEW_SUBSCRIPTION`). `sendOnboardingEmail` sends the trial variant: **no Telegram buttons at all** — announcement channel + signal groups are revealed only at conversion (the trial-group section was removed 2026-07-27), "First charge <cohort date>" framing — 16 August for DrWealth trials (`referralSource === "drwealth"`, sign-ups on/before 2 Aug), 9 August otherwise (sign-ups on/before 9 Aug); past each cutoff the email shows the subscriber's real trial end. Paid checkouts get the normal welcome.
2. **Trial converts** (`trialing → active`, first successful charge) → `TRIAL_CONVERTED` → `sendTrialConvertedWelcomeEmail` reveals the channel + signal groups.

> **A conversion needs a PAID invoice, not a status flip** (incident, 2026-08-03). The old rule here read "a failed conversion charge goes to `past_due`, not `active`, so the transition reliably means success". That holds for charges, but a trial can also be ended with no charge at all by an API or subscription-schedule write — which is what the standardiser did to two live trialists. Both went `trialing → active` carrying a **draft** invoice, and both were emailed "you're now a full subscriber", revealing the channel and signal groups, three weeks early having paid nothing. `TRIAL_CONVERTED` now additionally requires `subscription.latest_invoice` to be `paid`; an unpaid flip logs loudly and emits nothing. The spurious-`PLAN_CHANGED` suppression stays keyed on the raw status flip (`statusFlippedFromTrial`), so withholding a welcome can never turn into a plan-change email instead. Don't relax this back to a status check.
3. **Trial cancelled, ends without charging** → `ENDED` with `wasUnconvertedTrial` → `sendTrialEndedWinbackEmail`.

**Trial-end standardisation** (`lib/trial-standardiser.ts` + `api/standardise-trial-ends.ts`, daily cron `0 14 * * *` = **22:00 SGT** — scheduled early because Vercel Hobby fires a cron anywhere within the hour AFTER the scheduled minute (the old 23:55 schedule fired at 00:09 on 2026-08-04, past the deadline), so 22:00 + worst-case 59 min still lands before the 23:59 trial END. The one gap left: a final-day sign-up after the run keeps its rolling date — do a manual straggler check just after each cohort target passes): a payment link can only express a trial as a relative `trial_period_days`, so every sign-up gets its own end moment and the count drifts a day per day the link stays open. This cron pulls every trialing subscription on `TRIAL_PRICE_ID` onto its cohort's shared target (`TRIAL_COHORTS`, matched on `metadata.ref`, null-ref entry last as the catch-all), so a cohort converts together and the comms can promise one date. It **hard-sets** — a trial is moved whether that extends or shortens it (decision 2026-08-03; the links carry custom text naming the fixed date above the subscribe button, so sign-ups are told the real date before paying). Targets are **self-expiring**: once a target is past, that cohort is skipped and the job goes silent, so a finished campaign needs no cleanup and a new one needs only a new `TRIAL_COHORTS` entry. Two behaviours exist because a manual Python script got them wrong: a **schedule-managed subscription** (customer queued a plan change in the portal) rejects a direct `trial_end` write, so the schedule's phase boundary is moved instead, preserving the queued downgrade; and **one failure never aborts the run**

> **Never infer the trial flag when rewriting a schedule phase** (incident, 2026-08-03). A portal-created schedule can report `trial_end: null` on its FIRST phase while the subscription is still `trialing`. The adapter inferred the flag from that field, so the rewrite described a billable phase — Stripe ended two subscribers' trials immediately and raised a $417 draft invoice against each, three weeks early. Caught before finalisation; both voided with `attempted: false`, nothing charged, both restored to `trialing` with their downgrades intact. `shiftPhaseBoundary` now forces `trial: true` on the first phase unconditionally — it is only reached for a currently-trialing subscription, so that is always correct. Don't reintroduce inference. A **post-write check** is the second line of defence: the job re-reads every subscription it wrote to, and anything no longer `trialing` goes into `summary.endedTrials`, is kept out of the moved count, and fires a 🚨 ping. Moving a trial end is this job's only legitimate effect; ending one can no longer happen silently. Both paths were re-run against live Stripe after the fix (66 subscriptions, 4 via schedule including the two that broke) with zero ended trials. Note also that a subscription-created invoice **cannot be deleted** ("You can't delete invoices created by subscriptions"): to kill a positive one, set `auto_advance: false`, finalise with `auto_advance: false`, then void.
>
> **Restoring a wrongly-ended trial leaves a negative invoice behind — disarm it.** Undoing the conversion generated a −$416.99 "Unused time" DRAFT on each subscription: the credit side of a charge that never happened. Left alone it finalises and credits the customer, silently cancelling out their real first payment. For a NEGATIVE invoice do **not** finalise (that issues the credit) — set `auto_advance: false` and leave it as a draft, which never touches the customer balance. Verify with `customer.balance == 0` and an invoice preview showing the expected amount. — each subscription is independent and failures are reported in the ping. Verify against live Stripe without writing: `npx tsx --env-file=.env scripts/dry-run-trial-standardise.mts` (add `--schedule <id>` to inspect one schedule's phase mapping).

- **Win-back deliverability:** the win-back is deliberately NOT built with the branded `emailShell` — it's a plain personal note (no logo/CTA button/dollar pitch) sent from a personal `From` name (`sendEmail`'s optional `from`), to favour Gmail's Primary tab over Promotions. Gmail still decides the tab per recipient, so this is best-effort (decision 2026-07-27).
- **Spurious `PLAN_CHANGED` guard (don't re-open):** at `trialing → active`, Stripe includes `items` in `previous_attributes` with the SAME price (the item's period changed). The plan-change branch therefore only fires when the price ID actually changed and never on a trial conversion — otherwise every converter got a bogus "plan changed" email + TV churn. Verified with a Stripe test clock; covered by `stripe-translator.test.ts`.

## Sheet schema (A–P webhook block + manual Q–S + T–V)

Data starts at row 2; row 1 is headers. Subscriber primary key for dedup is **email**; the post-checkout lookup key is **Stripe Subscription ID** (col O). `bot.py` (separate repo) reads this same sheet and owns col P.

`A` Email · `B` Customer Name · `C` TradingView Username · `D` Telegram Username · `E` Status (`ACTIVE`/`PAYMENT_FAILED`/`CANCELLATION_SCHEDULED`/`CANCELLED`/`TRIAL_ACTIVE`/`TRIAL_CANCELLATION_SCHEDULED`/`TRIAL_CANCELLED` — the `TRIAL_` variants behave exactly like their paid counterparts for access; `TRIAL_CANCELLED` means a trial that ended without ever converting; a trial's first paid charge lands on plain `ACTIVE`) · `F` Current Plan · `G` Latest Action · `H` Previous Plan · `I` Subscription Price · `J` Coupon Discount (coupon-code text, e.g. `NAV30`; blank = none) · `K` Subscription Start · `L` Subscription Expiry · `M` Subscription Count · `N` Failed Payment Count · `O` Stripe Subscription ID · `P` Telegram User ID (bot-owned).

**Q–S are manual columns Joseph maintains by hand — the code must NEVER write them:** `Q` Indicator Invited · `R` NOTES · `S` Pepperstone Acc. They exist only in the live sheet, not in this codebase's write paths (`appendNewSubscriber` batch-writes A–P and T as two separate ranges precisely to skip them).

`T` **Referral Source** — partner attribution (e.g. `drwealth`), written on STARTED from the checkout session's `client_reference_id`, which the website appends to the payment-link URL when the visitor landed with `?ref=<partner>` (see `web/src/scripts/referral.ts`). First-touch wins: a reactivation only fills an empty cell, never overwrites. The translator also stamps the ref as `metadata.ref` on the Stripe subscription so attribution survives outside the sheet.

`U` **Follow-up Sent** — written by the T+1 onboarding follow-up cron (`lib/followup.ts` + `api/followup-send.ts`, daily 20:00 SGT = `0 12 * * *` UTC in `vercel.json`): selects `ACTIVE` or `TRIAL_ACTIVE` (trialists keep getting the follow-up), never-renewed (`subscriptionCount === 1`), col-U-blank rows 1–14 SGT calendar days after Subscription Start (go-live floor `FOLLOWUP_NOT_BEFORE = 2026-07-23`) and stamps the SGT send timestamp here. The blank cell IS the once-only guard — never backfill it by hand.

`V` **Mobile Number** — E.164 phone from Stripe checkout (`customer_details.phone`), written on STARTED when the payment link has `phone_number_collection` enabled (trial links from 2026-07-25 onward; older links don't collect it, so V is blank for earlier subscribers). Reactivations refresh it when checkout provides a number. The next webhook-owned column goes at W onward.

Col J holds the coupon code as plain text (`NAV30` / `NAV21` / `SK50`; blank = no coupon) — it stopped being a checkbox on 2026-08-06. The webhook writes the code resolved from the subscription's discounts (promotion code → `COUPON_CODES` map in `plans.ts` → coupon name → coupon ID); `parseRow` still understands legacy `TRUE`/`FALSE` cells (TRUE = discounted, code unknown). `SheetRow` carries both `couponCode` (the cell text) and the derived `couponDiscount` boolean.

### Status Log tab (append-only, 9 cols A–I)

Same spreadsheet, tab `Status Log` (override with `GOOGLE_SHEET_LOG_TAB_NAME`). One row appended per lifecycle event; rows are never edited or deleted — it's the source for renewal-rate, churn-cohort, and cancel-then-undo analysis.

`A` Timestamp (`2026-07-09 14:32:05`, SGT, sortable) · `B` Email · `C` Stripe Sub ID · `D` Action · `E` Plan · `F` Previous Plan · `G` Price · `H` Coupon (`TRUE`/`FALSE` text, not a checkbox) · `I` Detail (free text: expiry, attempt count, cancellation reason, promo code).

Action values: the Latest Action set (now including `START_TRIAL`, trial sign-ups' counterpart to `NEW_SUBSCRIPTION`) plus `ENDED`, `CANCELLATION_REASON` (carries the subscriber's reason/comment in Detail), `PRICE_SYNC` (same-plan price migration), and `TELEGRAM_REMOVED` (one row per instant group removal — Detail lists removed/skipped/failed groups and any identity mismatch, prefixed `dry run — ` while `TELEGRAM_KICK_DRY_RUN` is on; written for the fail-safe short-circuits too, since those mean the remover ran and decided to do nothing). Duplicate Stripe deliveries log nothing — the idempotency guards return before the log write. **Keep this tab free of data validation and stray values** — `appendEventLogRow` relies on `values.append` table detection, which the Subscribers tab's trailing checkbox validation famously broke.

## Plans & prices

`lib/plans.ts` holds `PRICE_TO_PLAN` (both **live and test** price IDs — they're globally unique so they coexist) and `PLAN_PRICE_SGD_QUARTERLY` (drives UPGRADED/DOWNGRADED/PLAN_SWITCH). Update both whenever a Stripe price is added or replaced. **When a price rises, add the new price ID but keep the old one** — grandfathered subscribers stay on the old ID and their renewals must still resolve. The plan strings here are mirrored by hand in the bot's `config.py` — keep them aligned.

Two things the plan *code* hides: (1) **display names can differ from codes** — e.g. `US_SG_FXMC` shows as "US + FXMC" (`PLAN_DISPLAY_NAMES`); (2) **every combo grants the SG market as a free bonus** — `parsePlanType()` appends `SG` to any combo that doesn't already name it (so `US_HK` → US/HK/SG). SG is a combo + All-Markets perk only; the single major plans don't include it. The same rule is mirrored in `config.py` `plan_markets()`.

## Dev, test, deploy

- **Env vars:** full list and meaning in `README-webhook.md`. Production values live in the Vercel dashboard; `.env` is local-dev only. Never commit real keys. Where each shared secret lives across runtimes: `../Navigator Business Resources/secrets-map.md`.
- **Typecheck:** `npx tsc --noEmit` (or `npm run typecheck`). Keep it green.
- **Tests:** `npm test` (vitest). `lib/subscription-lifecycle.test.ts` drives the lifecycle with in-memory fakes — no Stripe payloads, no network. Add a test before changing lifecycle behaviour.
- **Local webhook testing:** `npx vercel dev` + `stripe listen --forward-to localhost:3000/api/stripe-webhook`, then `stripe trigger <event>`. Details in `README-webhook.md`.
- **Lifecycle tests:** every collaborator (`SubscriberStore`, `Mailer`, `AdminNotifier`) is an interface — drive the lifecycle with plain `SubscriberAction` objects and in-memory fakes; no Stripe payloads needed.
- **Deploy:** push to `main`; Vercel auto-deploys. The Playground workspace has a `/push-website` skill for this.
- **Don't run `npm run build` against `web/` while its dev server is live** — it corrupts the dev server's Vite cache (page serves correct SSR HTML but renders unstyled in-browser). Fix: stop the dev server, delete `web/node_modules/.vite`, restart.
